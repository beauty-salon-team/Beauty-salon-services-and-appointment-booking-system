مستند تصمیم‌های طراحی و فنی سامانه سالن زیبایی

۱. مقدمه

این مستند تصمیم‌های اصلی طراحی و فنی گرفته‌شده در پروژه سامانه خدمات و رزرو نوبت سالن زیبایی را توضیح می‌دهد. هدف از این تصمیم‌ها، ایجاد سامانه‌ای ساده، قابل نگهداری و متناسب با نیازهای پروژه است.

۲. انتخاب معماری نرم‌افزار

تصمیم: استفاده از معماری لایه‌ای (Layered Architecture) با ساختار یکپارچه (Monolithic).

دلیل انتخاب: این معماری برای پروژه‌های کوچک و تیم‌های کم‌جمعیت مناسب است. همچنین باعث جداسازی رابط کاربری، منطق برنامه و دسترسی به داده‌ها می‌شود و توسعه، آزمایش و نگهداری سامانه را آسان‌تر می‌کند.

۳. انتخاب فناوری‌ها

۳.۱. فناوری سمت کاربر

تصمیم: استفاده از React.js.

دلیل انتخاب: این فناوری امکان ساخت رابط کاربری تعاملی و استفاده‌ی مجدد از اجزای رابط کاربری را فراهم می‌کند.

۳.۲. فناوری سمت سرور

تصمیم: استفاده از Node.js و Express.js.

دلیل انتخاب: این فناوری‌ها امکان پیاده‌سازی منطق برنامه و ایجاد رابط‌های برنامه‌نویسی (API) را به شکلی ساده و انعطاف‌پذیر فراهم می‌کنند.

۳.۳. پایگاه داده

تصمیم: استفاده از PostgreSQL.

دلیل انتخاب: این پایگاه داده‌ی رابطه‌ای برای ذخیره و مدیریت اطلاعات مشتریان، متخصصان زیبایی، خدمات، برنامه‌های کاری و نوبت‌ها مناسب است و به حفظ ارتباط و یکپارچگی داده‌ها کمک می‌کند.

۴. تصمیم‌های مربوط به طراحی پایگاه داده

تصمیم: در نظر گرفتن موجودیت‌های جداگانه برای مشتری، متخصص زیبایی، خدمت، برنامه‌ی کاری و نوبت.

دلیل انتخاب: جداسازی این موجودیت‌ها از تکرار غیرضروری اطلاعات جلوگیری می‌کند و مدیریت نوبت‌ها، خدمات سالن و برنامه‌ی کاری متخصصان را آسان‌تر می‌سازد.

۵. طراحی ارتباط بین بخش‌های سامانه

تصمیم: استفاده از رابط‌های برنامه‌نویسی REST برای ارتباط بین بخش کاربر و سرور.

دلیل انتخاب: این روش ارتباطی ساختاری منظم برای ارسال و دریافت اطلاعات فراهم می‌کند و جداسازی بخش‌های مختلف سامانه را آسان‌تر می‌سازد.

۶. احراز هویت کاربران

تصمیم: در صورت پیاده‌سازی احراز هویت، استفاده از روش مبتنی بر توکن مانند JWT بررسی می‌شود.

دلیل انتخاب: این روش می‌تواند به شناسایی کاربران و محافظت از بخش‌هایی که نیاز به دسترسی مجاز دارند کمک کند.

۷. روش توسعه‌ی پروژه

تصمیم: استفاده از روش اسکرام (Scrum) و تقسیم فرایند توسعه به دو اسپرینت (Sprint).

دلیل انتخاب: تقسیم کار به بازه‌های کوتاه‌تر، اولویت‌بندی قابلیت‌ها، پیگیری پیشرفت و بهبود تدریجی سامانه را آسان‌تر می‌کند.

۸. قابلیت‌های قابل توسعه در آینده

در نسخه‌های آینده می‌توان قابلیت‌هایی مانند پرداخت آنلاین، ارسال اعلان و امکانات بیشتر برای مدیریت سالن را اضافه کرد. در صورت افزایش پیچیدگی سامانه، معماری آن نیز قابل بازبینی خواهد بود.

۹. نتیجه‌گیری

تصمیم‌های فوق با هدف ایجاد سامانه‌ای منظم، قابل توسعه و قابل نگهداری گرفته شده‌اند. این انتخاب‌ها با نیازهای فعلی پروژه و امکانات یک تیم دانشجویی متناسب هستند.
