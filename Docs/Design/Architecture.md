مستندات معماری پروژه Beauty Salon Appointment System

۱. انتخاب معماری (Architecture Choice)

با توجه به کوچک بودن تیم توسعه و اینکه پروژه سیستم رزرو نوبت سالن زیبایی در مرحله طراحی و پیاده‌سازی اولیه قرار دارد، معماری Layered Monolith (معماری تک‌پارچه لایه‌ای) برای این پروژه انتخاب می‌شود.

در این معماری، بخش‌های مختلف سیستم در قالب یک برنامه واحد پیاده‌سازی می‌شوند، اما مسئولیت‌های مربوط به رابط کاربری، منطق کسب‌وکار و دسترسی به داده‌ها از یکدیگر جدا هستند.

دلایل انتخاب این معماری عبارت‌اند از:

* سادگی و سرعت توسعه: این معماری برای تیم‌های کوچک مناسب است و امکان پیاده‌سازی قابلیت‌های اصلی سیستم را با پیچیدگی کمتر فراهم می‌کند.
* کاهش هزینه و پیچیدگی: در مقایسه با معماری Microservices، نیازی به استقرار و مدیریت چند سرویس مستقل نیست.
* جداسازی مسئولیت‌ها (Separation of Concerns): هر لایه وظایف مشخصی دارد و این موضوع باعث خوانایی بهتر کد و نگهداری آسان‌تر سیستم می‌شود.
* امکان توسعه در آینده: در صورت افزایش کاربران یا گسترش قابلیت‌های سامانه، می‌توان بخش‌های مختلف را به‌تدریج توسعه داد.

این معماری برای نیازهای فعلی سیستم رزرو نوبت سالن زیبایی مناسب است؛ زیرا امکانات اصلی پروژه شامل ثبت‌نام کاربران، مشاهده خدمات، انتخاب متخصص و رزرو و مدیریت نوبت‌هاست.

۲. لایه‌های سیستم و فناوری‌های مورد استفاده

سیستم بر اساس معماری لایه‌ای طراحی می‌شود. هر لایه مسئولیت مشخصی دارد و از طریق ارتباط تعریف‌شده با سایر لایه‌ها همکاری می‌کند.

۲.۱. لایه نمایش (Presentation Layer)

این لایه مسئول ارتباط مستقیم با کاربران و نمایش اطلاعات سیستم است. مشتریان از طریق این لایه می‌توانند ثبت‌نام کنند، وارد حساب کاربری خود شوند، خدمات و قیمت‌ها را مشاهده کنند، متخصص موردنظر خود را انتخاب کنند و نوبت رزرو کنند.

همچنین، امکانات مربوط به مدیریت خدمات و مشاهده یا مدیریت نوبت‌ها برای مدیر سیستم در این لایه قابل ارائه است.

فناوری‌های این لایه با توجه به ابزارهای انتخاب‌شده برای رابط کاربری پروژه تعیین می‌شوند. در صورت استفاده از رابط وب، می‌توان از HTML، CSS و JavaScript یا چارچوب‌هایی مانند React استفاده کرد.

۲.۲. لایه منطق کسب‌وکار (Business Logic Layer)

این لایه مسئول اجرای قوانین و منطق اصلی سیستم است. وظایف آن شامل اعتبارسنجی اطلاعات ثبت‌نام و ورود کاربران، بررسی اطلاعات خدمات، مدیریت درخواست‌های رزرو، بررسی زمان‌های در دسترس متخصصان و جلوگیری از ثبت نوبت‌های متداخل است.

همچنین، این لایه وضعیت نوبت‌ها را مدیریت می‌کند و اطمینان می‌دهد که درخواست‌های کاربران مطابق قوانین سیستم پردازش شوند.

برای پیاده‌سازی این لایه، در صورت استفاده از فناوری‌های مبتنی بر JavaScript، می‌توان از Node.js و Express استفاده کرد.

۲.۳. لایه دسترسی به داده‌ها (Data Access Layer)

این لایه مسئول ارتباط با پایگاه داده و انجام عملیات مربوط به ذخیره‌سازی، بازیابی، به‌روزرسانی و حذف اطلاعات است.

اطلاعات کاربران، خدمات سالن زیبایی، متخصصان و نوبت‌ها در این لایه مدیریت می‌شوند. همچنین، ارتباط بین جداول و رعایت کلیدهای اصلی و خارجی باید به‌گونه‌ای انجام شود که یکپارچگی اطلاعات حفظ شود.

پایگاه داده پروژه بر اساس ساختار طراحی‌شده شامل موجودیت‌های Users، Services، Specialists و Appointments است. نوع پایگاه داده و ابزار دسترسی به آن باید مطابق فناوری‌هایی باشد که تیم در پیاده‌سازی واقعی پروژه انتخاب کرده است
۳. طراحی رابط برنامه‌نویسی (API Design)

برای ارتباط بین رابط کاربری و بک‌اند، می‌توان از REST API استفاده کرد. در این روش، درخواست‌های HTTP برای ارسال و دریافت اطلاعات به کار می‌روند و داده‌ها می‌توانند در قالب JSON منتقل شوند.

مسیرهای پیشنهادی API برای سیستم سالن زیبایی عبارت‌اند از:

* GET /api/services : دریافت فهرست خدمات فعال سالن زیبایی.
* GET /api/services/:id : دریافت اطلاعات یک خدمت مشخص.
* GET /api/specialists : دریافت فهرست متخصصان فعال.
* GET /api/specialists/:id : دریافت اطلاعات یک متخصص مشخص.
* POST /api/auth/register : ثبت‌نام کاربر جدید.
* POST /api/auth/login : ورود کاربر به سیستم.
* GET /api/appointments : مشاهده نوبت‌ها بر اساس سطح دسترسی کاربر.
* GET /api/appointments/:id : مشاهده جزئیات یک نوبت مشخص.
* POST /api/appointments : ثبت نوبت جدید.
* PATCH /api/appointments/:id : به‌روزرسانی اطلاعات یا وضعیت نوبت در صورت مجاز بودن.
* DELETE /api/appointments/:id : لغو یا حذف نوبت مطابق قوانین سیستم.
* POST /api/services : ثبت خدمت جدید توسط مدیر مجاز.
* PATCH /api/services/:id : ویرایش اطلاعات خدمت توسط مدیر مجاز.

این مسیرها ساختار پیشنهادی API هستند و باید با کد واقعی بک‌اند هماهنگ شوند. مسیرهای مدیریتی باید فقط برای کاربران دارای مجوز قابل استفاده باشند.

۴. امنیت و کنترل دسترسی

امنیت یکی از ملاحظات مهم در طراحی سیستم رزرو نوبت سالن زیبایی است. اطلاعات حساب کاربران باید به‌صورت امن نگهداری شوند و رمزهای عبور نباید به شکل متن ساده در پایگاه داده ذخیره شوند.

در صورت پیاده‌سازی احراز هویت با JWT، توکن باید به‌درستی اعتبارسنجی شود و دسترسی کاربران بر اساس نقش و مجوزهای آن‌ها کنترل شود.

مشتریان باید فقط به اطلاعات و عملیات مجاز مربوط به حساب خود دسترسی داشته باشند. عملیات مدیریتی مانند ایجاد و ویرایش خدمات نیز باید به مدیران مجاز محدود شود.

همچنین، اطلاعات ورودی کاربران باید اعتبارسنجی شوند و خطاهای سیستم بدون افشای اطلاعات حساس مدیریت شوند.

۵. تصمیمات کلیدی و ملاحظات طراحی (Trade-offs)

در انتخاب معماری سیستم، سادگی توسعه و قابلیت نگهداری در اولویت قرار گرفته است. معماری تک‌پارچه لایه‌ای نسبت به Microservices پیچیدگی عملیاتی کمتری دارد و برای نیازهای فعلی پروژه مناسب‌تر است.

در مقابل، در معماری تک‌پارچه بخش‌های سیستم به‌صورت یک واحد مستقر می‌شوند؛ بنابراین، با رشد قابل‌توجه سامانه ممکن است نیاز به بهینه‌سازی یا جداسازی برخی بخش‌ها وجود داشته باشد.

در زمینه امنیت، استفاده از احراز هویت مناسب و کنترل دسترسی برای محافظت از اطلاعات کاربران و نوبت‌ها ضروری است. در زمینه صحت داده‌ها نیز بررسی تداخل زمانی نوبت‌ها و حفظ ارتباط صحیح بین جداول اهمیت دارد.

فناوری‌های پیشنهادی این مستند باید با ابزارهای واقعی استفاده‌شده در پروژه هماهنگ شوند. هر فناوری که هنوز انتخاب یا پیاده‌سازی نشده است، صرفاً پیشنهاد محسوب می‌شود و نباید به‌عنوان قابلیت تکمیل‌شده معرفی شود.

۶. جمع‌بندی

معماری پیشنهادی سیستم رزرو نوبت سالن زیبایی بر پایه معماری تک‌پارچه لایه‌ای طراحی شده است. این معماری مسئولیت‌های مربوط به نمایش اطلاعات، منطق کسب‌وکار و دسترسی به پایگاه داده را از یکدیگر جدا می‌کند.

با استفاده از این ساختار، امکان پیاده‌سازی قابلیت‌هایی مانند ثبت‌نام و ورود کاربران، مشاهده خدمات، انتخاب متخصص، ثبت و مدیریت نوبت‌ها و کنترل دسترسی فراهم می‌شود.

این طراحی با ساختار پایگاه داده و نیازمندی‌های سیستم رزرو نوبت سالن زیبایی هماهنگ است و می‌تواند مبنایی برای توسعه و نگهداری پروژه قرار گیرد.
